## 一、真实缺陷（会导致功能不可用或数据异常）

### 1. 失败任务永远无法用同一 requestId 重发 ★实测
`core-service.mjs:94-97`：只要 `requestId` 命中已有任务且参数一致，就直接原样返回那个任务对象，不重新提交。
实测结果：
```
首次任务状态: failed (not_configured)
同 requestId 重发 -> 返回 failed，id 仍是同一任务
同 requestId 换参数 -> conflict: 此任务 requestId 已用于另一请求
```
影响：任务一旦失败（密钥没配、网络超时、供应商报错），该 requestId 就是死 ID，只能换新 ID 重发。但 `task_start` 工具描述写的是"超时重试必须保留同一 ID 和全部参数"——**指引与实际行为相反**。

### 2. 同一 requestId 在项目版本变化后重试 = 死结 ★实测
`core-service.mjs:111` 的幂等 hash = `digest(input)`，包含 `expectedVersion`。
实测结果：
```
第一次更新 (版本 V1) -> OK
同 requestId、新版本重试 -> conflict: 此 requestId 已用于另一项操作，请勿改变重试参数
```
但工具描述要求"必须基于最近版本"，冲突后重新读取必然拿到新版本。于是：**冲突 → 重读 → 重试 → 又冲突**，只能换 ID。
更怪的是 `task_adopt` 的 hash 只算 `{taskId}`（`:111`），同一 ID 换版本重试是允许的（返回 `stale_result`）。**两个工具的幂等粒度不一致**。

### 3. 取消后完成的结果被静默丢弃
`tasks.mjs:26`：`update()` 遇到 `status === 'cancelled'` 直接返回旧值；`execute()` 第 37 行 `await update(id, {status:'succeeded', result})` 因此被吞掉。
影响：任务跑到 99% 被取消，生成结果（已付费的外部 API 结果）拿不回来，也无法 `task_adopt`。

### 4. `dismiss` 不释放占位，`uncertain` 任务永久阻塞同类新任务
`tasks.mjs:56` 计算 `unfinished` 时**没有过滤 `dismissed`**，且 `unfinished` 包含 `uncertain`。
- 网页点"忽略"后，任务在列表消失，但同项目同类型的新任务仍被 `409 pending_task` 拒绝；
- 崩溃恢复会把 `queued/running/waiting_external` 标成 `uncertain`（`:14`），重启后该对象**再也提交不了**，必须先 `task_cancel`——而 MCP 侧没有 dismiss 工具，只有 HTTP 有。

### 5. `workspace.previous.json` 只写不读
`repository.mjs:102、140` 每次写入都保留"上一版本快照用于恢复"，但全仓库**没有任何一处读取它**（已 grep 确认）。恢复能力是死代码，注释与实现不符。

### 6. 外部供应商配置在 MCP 侧不生效
- `service-settings.mjs:7` 允许通过 `/v1/settings` 配置的字段只有 4 个密钥 + 3 个 URL/模型，**不含 provider 开关**；
- `core-service.mjs:103` 对 `image/cover/video-shot/video-audio` 强制 `args.provider ??= 'workbuddy'`；
- 而 `adapters/images.mjs:5` 上报的 `provider` 读的是 `WORKBENCH_IMAGE_PROVIDER`，`adapters/video.mjs:4` 读 `VIDEO_PROVIDER`（**两个环境变量命名还不一致**）。
结果：在设置页填了图像密钥后，`workbench_status` 可能显示 `provider: external`，但 MCP 发起的任务仍走 WorkBuddy 交接。且这两个 provider 变量只能手改 `.env.local`，设置页改不了。

### 7. `project_deliver` 是"全有或全无"
`core-service.mjs:69`：`format:'all'` 时会遍历校验**所有**成品文件，任何一个缺失（比如迁移后少恢复一个 mp4）整个交付报 404，连小说 TXT 都拿不到。

### 8. 删除素材会触发难懂的校验失败
`repository.mjs:34、38`：`references[].assetId`、`concepts[].savedAssetId`、`coverAssetId` 都必须指向仍存在的素材。所以用 `project_update` 替换 `assets` 数组删掉某张图时，若忘了先清引用，会得到一个笼统的 `400 项目数据格式无效，未覆盖已有文件`，不告诉你是哪个引用断了。

## 二、功能不完善 / 半成品

### A. 文档已声明"本轮不做"（不算缺陷，但要清楚边界）
`docs/创意工作台验收条目.md:219` 明确不计入：**3D 资产、长篇编排、动态网站后台、云发布、未封装的管理操作（删除/备份/迁移）**。
README 第 7 行也自述"当前验证使用本地模拟，真实授权、生图效果和文化质量仍待验"。

### B. 实现层面的半成品
1. **文创（craft）类型是死胡同**：`project_create` 允许 `type:'craft'`，`contentKeys.craft` 也让内容生成能跑通，但没有 craft 专属的成品生成与交付（`workbench_status.scope` 自认"3D 未实现"）。选了它只能得到一堆文字。
2. **视频参数被硬编码**：`output-generation.mjs:41` 生成分镜时固定 `burnSubtitles:true, keepAudio:false`，用户通过 `project_update` 设的值在下一次重新生成分镜时被覆盖。
3. **有旁白时原片音轨必被丢弃**：`video-media.mjs:64-70`，`s.audio` 存在就只映射配音，即使 `keepAudio:true` 也拿不回原声。
4. **镜头时长不匹配时静默截断**：`:62` 只在切片比镜头短时报错，长于镜头时用 `-t s.duration` 直接裁掉，不提示。
5. **DeepSeek 两套并存实现**：`adapters/deepseek.mjs` 的 `completeCreativeBrief`（max_tokens 4096、独立校验）与 `adapters/text.mjs` 的 `generateJson`（max_tokens 8192、另一套校验）打同一个端点，行为/上限/错误信息都不一致。
6. **视频模型与地址写死**：模型固定 `gen4.5`，默认 base URL 是 `https://api.dev.runwayml.com/v1`（dev 域名）；`VIDEO_API_BASE_URL` 可改，但模型、Runway 版本号 `2024-11-06` 都不可配。
7. **字幕未转义**：`video-media.mjs:48` 只剔掉 `<>`，旁白里的 `{}`、`\`、`,` 会直接进 `subtitles=` 滤镜（非注入，但可能让滤镜解析异常）。
8. **生成包里的测试文档是旧的**：`scripts/workbench-setup.mjs:28` 把 `docs/WORKBUDDY_CORE.md` 拷成 `TESTING.md`，而官方清单已经是 `docs/创意工作台验收条目.md`（9 组约 90 项）。用户拿到的导入包里是过时的 6 条版本。
9. **mcp.json 硬编码 Node 绝对路径**：`command` 写的是生成时的 `process.execPath`（本机是 `~/.workbuddy/binaries/node/versions/22.22.2-2/bin/node`）。换 Node 版本/卸载后配置即失效。

### C. 完全没有清理机制（实测数据）
```
work/data/handoff   19 MB   （8 个任务目录，每个都留着 input PNG + result）
work/data/inbox    8.1 MB   （media_import 读完后源文件仍在）
work/data/tasks     164 KB  （16 个任务 JSON，永久累积）
work/data/exports     8 KB
```
- 没有删除项目、删除素材、清理任务、清理交接目录的**任何** MCP 工具（核心契约里 0 个删除类工具）；
- `repository.mjs:101` 注释写着"未被引用的媒体保留用于撤销/历史"——但没有撤销入口；

## 三、操作逻辑很奇怪的地方

1. **"保留同一 ID 重试"与"必须基于最新版本"互斥**（见缺陷 1、2）。
2. **`task_get` 对 `uncertain` 的提示自相矛盾**：`core-service.mjs:27` 返回"核实原请求；不要更换 ID 自动重试"，但同 ID 事实上无法重发，最终只能换 ID。
3. **幂等收据永久缓存结果**：`repository.mjs:110-115`，同一个 `operationId` 永远返回第一次的结果并带 `replayed:true`，上限 1000 条（`slice(-1000)`）。收据存在 `workspace.json` 里，会让这个文件持续变大（当前已 52 KB）。
4. **所有 MCP 工具都标注 `idempotentHint: true`**（`workbench-mcp.mjs:19`），但 `task_start` 对失败任务只是"重放失败"，并非真正可重放。
5. **Web 有 `dismiss`，MCP 没有**：`http-server.mjs:115` 提供 `POST /v1/tasks/{id}/dismiss`，12 个 MCP 工具里没有对应项，网页端能做的操作在对话里做不了。
6. **全局忙计数共享**：`http-server.mjs:43` 的 `active` 同时给"创意生成"和"媒体上传"用，且硬上限 2。生成一段创意时上传视频会被 429。
7. **图片一律重编码**：`putImage` 无论源格式都用 sharp 转 PNG（`:185`），JPEG/WebP 都会变大、EXIF 全丢；同理 `importMedia` 对合规 MP4 也强制 libx264 重编码一遍。
8. **命名与行为错配**：`workbench_status` 返回体里带 `workbuddyClientTest: "pending-manual"`——一个运行时接口里塞了人工测试标记。
9. **`saveWorkspace` 的 writeId 语义混乱**：`:94-97` 同一个 `writeId` 内容变了报 `conflict`（"同一保存请求的内容发生变化"），但正常重试本来就该用同一 writeId 提交同样内容；而想重试不同内容又必须换 writeId，等于没有重放保护。
10. **项目上限 500、引用 100、概念 100、素材 500，但 `project_list` 没有分页**（`core-service.mjs:80` 一次全返回）。

## 四、安全与健壮性（整体做得不错，仅列残留项）

**做得好的**：Runtime 只监听 `127.0.0.1`（`workbench-http.mjs:7`）；Host/Origin 双重校验（`http-server.mjs:53`）；视频下载地址走域名白名单 + 不外传凭据（`adapters/video.mjs:35-38`）；网站预览带严格 CSP（`website.mjs:4`）；inbox/handoff 路径穿越防护；密钥文件 `0600` 且 `work/` 已被 `.gitignore`；原子写 + 重试。

**残留风险**：
- Runtime HTTP 接口**无任何鉴权**，同机任意进程都能读写/覆盖全部项目数据（靠 127.0.0.1 + Host 头兜底）。
- 密钥以**明文 JSON** 存在 `work/service-settings.json`（权限 0600，风险可控但仍是明文）。
- `/v1/files/restore/*` 对 html/zip/srt 只做魔数/体积检查（`http-server.mjs:93`），对 mp4/wav 存的是原始字节而非规范化后的字节。
- `service-settings.mjs:12`：值里禁止 `\r\n\0`，但**没有禁止其它字符**，也没有校验密钥格式。
- 单文件 `workspace.json` + 乐观锁：只适合单人单机，无并发能力（注释也承认"不把实时协同编辑算作已实现"）。

## 五、建议修复优先级

1. **P0**：统一软链接判定为 `path.startsWith(root + sep)`（同时修 `readHandoff`、`readInbox`）；放宽/修正 `media` schema 以容纳 `width/height/videoCodec/audio/subtitleFileId`。
2. **P0**：给失败任务一条重发路径（例如 `task_start` 增加 `retry` 语义，或失败任务允许同 ID 重新提交）；把"保留同一 ID"的指引改成与实现一致。
3. **P1**：`unfinished` 过滤 `dismissed`；取消后仍能取回已完成结果；把 `workspace.previous.json` 接上恢复入口或删掉这套写入。
4. **P1**：provider 开关纳入 `/v1/settings`，并让 `task_start` 默认值跟随服务端配置。
5. **P2**：补删除/清理能力（至少清理 handoff 与 inbox）；`project_deliver` 改为部分成功；生成包改用新的验收清单文档。
6. **P2**：视频 `burnSubtitles/keepAudio` 尊重用户设置；统一 DeepSeek 两套实现。
