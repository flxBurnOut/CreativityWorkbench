# 创意工作台内存与存储审计（2026-09-10）

## 结论与证据范围

存在多个可以复现的资源生命周期缺陷，已修复本轮确认的重复读取、重复解包、预览整文件缓冲、测试临时目录残留及部分关闭清理问题。当前 C 盘大体积占用也来自开发工具、宿主和安装器；不能全部归因于工作台生成任务。

本次检查了实际项目数据、相关进程、系统内存与分页文件、C 盘临时目录及宿主目录，并做了两次同权限的重点目录采样。目录扫描只读文件元数据，跳过符号链接和目录联接。部分系统文件锁定或无权读取；不同权限扫描结果不能直接相减当作增长率，AppData 虚拟化路径也不能简单相加。

用户项目、作品、历史版本和现有 C 盘缓存均未执行批量删除。3D 功能没有实施。本次没有进行真实 WorkBuddy 供应商生成、宿主长时内存录制或系统级逐次文件写入追踪。

### 任务包清理判断

不能把“任务执行过”直接当作删除整个目录的依据。原图、输入资料、请求清单和历史源码仍可能用于返工、来源检查、下载及恢复。

现有 `storage_cleanup` 扩展为逐文件识别：只列出已经成功接收、正式副本仍存在且两份 SHA-256 一致的源 ZIP；执行时再核对清单，保留原请求、输入、任务历史和正式成品。无法证明安全的副本保留。受保护或仍有活动任务的 inbox 文件不清理。

在用户真实数据上仅运行了清理预览：3 个已完成网站的 `result.zip`，共 4,318,729 字节（4.12 MiB）。没有执行删除。旧音视频若规范化后字节不同且无充分接收凭证，也不会冒险删除。

## 内存实测与根因

系统约 31.44 GiB 可见物理内存，采样时可用约 9.92 GiB。Windows 内存压缩进程约 4.12 GiB，但这代表全系统压力，不能归属本项目。

重启前，创意工作台 Runtime 工作集约 76 MiB；开发前端在代码热更新过程中约 246–489 MiB，私有提交约 946–1104 MiB；workerd 工作集约 151–185 MiB。工作集、私有提交和分页文件容量是不同指标，不能直接相加或把提交量当作物理常驻量。

同时运行的另一组 8790/3000 服务属于生产工作台；本项目使用 8791/3001，未发现它们是同一项目误启动的重复服务。本次只重启创意工作台。Codex、WorkBuddy、浏览器和工具进程也有明显常驻占用，没有擅自终止这些宿主进程。

### 本轮已修复的路径

1. **历史网站轮询重复读完整项目。** 任务列表把已读项目传给网站结果同步；30 个成功历史任务的回归中，从每任务再次读取降为整次列表读取 1 次。版本冲突仍重新读取核对，不覆盖新请求。
2. **同一个网站 ZIP 多次严格解包。** 按实际内容 SHA-256 缓存验证元数据，上限 128 项，不保留展开文件内容；完成、接收、同步链路复用验证结果。
3. **网站导入先写出重复/无效正式文件。** 完成入口先验证再交给原任务接收，正式存储由接收器负责；无效或冲突 ZIP 不再产生这类孤立输出。
4. **开发预览先读完整媒体。** 改为带背压的流式转发；预览关闭、请求断连或超时时中止上游并释放读取器，保留 Range、CSP 与路径限制。
5. **折叠的旧预览仍运行。** 两处旧网站预览折叠区只在打开时创建 iframe，关闭即卸载。默认新网站界面的布局保持不变。
6. **失败写入遗留临时文件。** 原子写入和原任务交接在写失败、空间不足、重命名失败后清理本次独占创建的临时文件，不删除其他写入者文件。
7. **测试与验证目录越积越多。** 改为统一创建、登记并等待服务/任务停止后清理；停止失败会保留目录并明确报错，避免存活进程向已删目录继续写入。内存验证默认删除大型测试数据，只有显式 `--keep-fixtures` 才保留。完整测试并发限制为 2，降低测试峰值。
8. **项目进程默认使用 C 盘 Temp。** 启动前预加载项目临时目录配置，覆盖当前进程与子进程的 TEMP/TMP/TMPDIR；不改 Windows 用户级环境变量。Vite、Miniflare、测试等新临时数据使用当前检出的 `work/tmp/process`。npm 自身及独立宿主的缓存不受此设置控制。
9. **失败的 MCP 自动启动留下子进程、启动日志无限累积。** 启动失败时停止本次新启动进程，不终止既有共享服务；启动时对达到 5 MiB 的 Runtime 日志轮换，保留 3 个归档。轮换发生于启动时，不是运行中的实时硬上限。
10. **开发缓存迁移后浏览器混用两份 React。** 真实页面复测发现 Vite 未把 cacheDir 纳入依赖版本，而带旧版本的依赖响应被浏览器长期缓存。缓存路径现在同时参与插件名和版本哈希；不同检出目录、serve/build 缓存隔离，正常重启仍能复用缓存。
11. **HTTP 已断连但后台文件仍在写入。** 关闭流程同时追踪 HTTP 在途处理与任务工作器，取消可中止的直媒体导入/创意生成，并等待处理结束；测试中用真实 POST 和可控磁盘写入验证“断连不等于处理完成”。

## 本轮验证

- 新增资源生命周期测试 20/20 通过，覆盖流式转发、背压、断连、文件失败清理、安全副本回收、轮询读取次数、关闭等待、失败启动、日志轮换及停止失败保留夹具。
- 最终全量测试：164 项中 162 项通过，2 项为已有 Windows 差异：目录别名测试创建链接时 EPERM，以及文件模式 0666 与 POSIX 0600 断言不一致。没有将这两项计为通过。
- lint、typecheck、build 通过。真实浏览器在构建后刷新、完整停止并重新启动后均能打开用户项目“岭南风文旅网站”，呈现“廊下岭南”网站；无 Runtime Error。进入项目为 1 个预览 iframe，回项目列表为 0，再进入恢复 1 个。只做本地页面与导航检查，没有创建新作品或发起供应商生成。
- 内存回归：同一 Runtime 内做 300 次图片状态轮询、30 次网站交接、120 次 Range 请求，包含 16 MiB ZIP/媒体夹具。第 10 到 30 轮 GC 后堆从约 18.04 到 19.04 MiB，增加约 1.00 MiB；采样 RSS 最高约 290.4 MiB，最后约 274.4 MiB，任务缓存约 2.03 MiB且受上限约束。
- 全量测试与默认内存验证结束后测试夹具目录为空，旧 C 盘 `creative-*` 没有增加。

上述采样不是瞬时峰值，也不是 WorkBuddy 或浏览器长时验收；不能据此宣布所有泄漏已经解决。

## 尚需继续治理的结构性压力

| 优先级 | 已确认的设计压力 | 后续方向 |
| --- | --- | --- |
| 高 | `/v1/tasks` 仍返回项目全量历史任务，部分任务带大段提示词和输入清单；UI 限制显示条数不能限制响应体 | 轮询只传任务摘要/修订变化，详情按需读取，保持现有 MCP 详情兼容 |
| 高 | 工作区轮询仍读取全量项目及历史后才比较版本 | 增加修订号/ETag 路径；历史大内容外置并按需加载，不删除用户历史 |
| 高 | 部分媒体上传/下载仍整文件缓冲，不同层的并发限制不是共享字节预算 | 共用媒体并发与内存预算、输入流落盘，避免多个大文件同时 Buffer.concat |
| 中 | JSON 备份含 base64，序列化与 Blob 可能持有多份大型内容 | 改为流式归档交付，维持旧备份兼容 |
| 中 | 多轮任务包重复携带既有素材/旧源码；这些也可能仍是有效返工依据 | 内容去重、引用清单、可重建任务包缓存，保留用户作品和来源记录 |
| 中 | 进程被强杀后可能留下 D 盘临时目录 | 引入明确所有者和存活检测的启动回收；仅迁移 TEMP 不等于垃圾回收 |
| 中 | 开发服务器与宿主本身常驻较重 | 对比赛使用方式比较构建后运行与热更新模式；单独做 WorkBuddy 真实长时观测 |

这些项目不宜在一次资源补丁中通过删除历史、放宽校验或改掉工作流来“解决”。本轮完成直接可验证的止增与生命周期修复，尚未实施以上接口和存储结构迁移。
