# 图片任务、结果与选用同步修复（2026-09-10）

当前核心协议 9、27 个工具、Skills 0.6.1。保持现有界面布局，修复成功图片未展示、不能从网页完成选用及旧重试混在当前任务中的问题。

## 本地复现与原因

用实际 PNG 和隔离项目复现了以下情况：任务为 succeeded、文件已保存，但概念对象的 candidateAssetId / savedAssetId 仍指向旧状态，因此对象卡片看不到结果。原实现需要额外 task_adopt 才把成功任务放入候选。

另外，生成依据包含整个概念对象，采用产生的候选 ID、提示词、选用和对比记录会使结果被自己的写入判为过期；仅 JSON 字段顺序改变也可能触发错误的过期判断。任务和项目分别轮询，没有对成功结果到达、页面恢复前台及迟到响应进行统一处理。

失败重试虽可能有 retryOf，旧请求没有统一的“已被接替”显示。不能据此推断任意同对象等待都属于重试。本次未拿到朋友实例中的具体任务记录，因此没有修改那份实际工作区。

## 已实现行为

1. **成功结果自动展示。** 原图片任务成功后，网页将结果投影到对应对象卡片，显示“新结果待选用”；无须 WorkBuddy 额外采用。原选用图保持到用户确认选用。
2. **网页完成最终选用。** “选用此图”调用共享 Runtime 的 image_select；修改图先打开实际原图与结果对比，填写观察记录后确认。同一次写入保存图片、对象的候选和选用引用、对比记录与历史；具有版本校验和幂等回执。
3. **采用状态明确。** task_get / task_list 返回 imageState，区分 unbound、candidate、selected。已被 WorkBuddy 放入候选的结果仍可在页面直接选用；已选用则无需重复 task_adopt。
4. **只排除虚假的过期。** 来源比较忽略 JSON 对象字段顺序，并在已绑定该结果时仅撤回该结果自身写入的字段进行比较。用户实质修改对象、要求或原图仍阻止旧结果覆盖新稿。选用最新图后，较早的未用结果留在任务记录，不抢占对象卡片。
5. **重试关系与执行状态分开。** 新重试明确保存 retryOf / supersededBy；已有明确 retryOf 的旧记录在启动时修复。旧等待显示已被接替并进入历史，executionStatus 保留原执行状态。旧文件晚到仍可查原 ID，不覆盖当前图。
6. **未关联的旧等待可确认修复。** 页面提供“这个等待已有后续结果？”入口；确认两者是同一次重试后关联到同项目、类型、对象的成功后续任务。没有确认的等待不会被猜测删除。对应接口是 task_dismiss 的 replacementTaskId，不取消远端作业。
7. **刷新不重新生成。** 页面恢复前台、pageshow 和“刷新任务与图片”会刷新状态。轮询只保留一个当前请求；强制刷新、切换项目或卸载时取消旧请求，丢弃乱序迟到响应。不缓存图片二进制，也不因等待自动追加生图请求。

task_adopt 对图片仍只放入候选；media_import 仍只做文件入库。两个操作都不冒充最终选用。网页任务始终沿用原 handoff ID 和路径。

## WorkBuddy 更新与复测

1. 更新代码后重启共享 Runtime 和网页服务；重新打开工作台页面。旧 Runtime 会被协议检查识别，不能只换 Skill 而继续使用旧服务。
2. 执行 `npm run workbench:setup` 生成本机包；重新导入 `work/workbuddy-core/creativity-project.zip`、`creativity-media.zip`，重新连接 MCP。应看到协议 9、27 个工具和 image_select。连接路径未变化时不必重复改连接配置。
3. 网页对已选用图片发起局部修改，让 WorkBuddy **只完成网页原任务的 PNG 交接**。检查原 ID 为 succeeded 后，页面自动出现“新结果待选用”，可对比并选用，离开再进入仍为新图。
4. 再测试 WorkBuddy 先 task_adopt 的候选路径，页面同样可选用；确认实际改动不明显时可以不选用，原图保留。
5. 检查旧重试：明确有 retryOf 的旧等待应进入历史；没有关联的，只在确认两个任务属于同一次重试时使用页面的接替入口。不要为清理状态重新生成图片。

若仍异常，记录项目 ID、原 taskId、后续 taskId、imageState、页面所在步骤及当时的具体操作。无需发送密钥。
